### 1.2 核心架构问题修复

**目标**：解决 LVGL/AEC/任务调度冲突

#### 任务 1：任务优先级重新设计

**问题**：
- 当前任务优先级混乱，导致音频处理被打断
- LVGL 定时器抢占了 AEC 音频处理时间

**解决方案**：
1. 创建统一的优先级定义文件 `main/core/task_priorities.h`
2. 明确优先级分层：
   ```cpp
   // 最高优先级：实时音频处理
   #define TASK_PRIORITY_AUDIO_AEC    23
   #define TASK_PRIORITY_AUDIO_INPUT  22
   #define TASK_PRIORITY_AUDIO_OUTPUT 21

   // 中等优先级：UI 渲染
   #define TASK_PRIORITY_LVGL_TIMER   10
   #define TASK_PRIORITY_DISPLAY      9

   // 低优先级：网络通信
   #define TASK_PRIORITY_NETWORK      5
   #define TASK_PRIORITY_MQTT         4
   #define TASK_PRIORITY_HTTP         3

   // 最低优先级：后台任务
   #define TASK_PRIORITY_BACKGROUND   1
   ```

3. 全局审查所有 `xTaskCreate` 调用，统一使用新定义
4. 添加优先级反转保护（使用 FreeRTOS 优先级继承互斥锁）

**产出文件**：
- `main/core/task_priorities.h`（新文件）

---

#### 任务 2：LVGL 定时器优化

**问题**：
- 5ms 的 LVGL tick 周期导致 AEC 音频中断冲突
- GIF 渲染时单次执行时间过长，触发看门狗

**解决方案**：
1. 固定 LVGL tick 周期为 **20ms**（基于 commit 2d339ef 的经验）
2. 实现 LVGL 任务与音频任务的互斥锁机制：
   ```cpp
   class DisplayLockGuard {
       // 在 LVGL 绘制前检查音频任务状态
       // 如果音频正在处理，延迟 LVGL 绘制
   };
   ```
3. 添加看门狗保护：
   - 单次 LVGL 渲染不超过 100ms
   - 每 50ms 喂狗一次
4. GIF 解码分块处理：
   - 每解码 10 帧暂停一次
   - 允许高优先级任务抢占

**产出文件**：
- `main/display/lvgl_display/lvgl_task.cc`（重构）
- `main/display/lvgl_display/gif/gifdec.c`（添加看门狗）

#### 任务 3：内存管理策略

**问题**：
- GIF 解码导致内存崩溃（commit c2dba9b）
- 内存碎片化严重
- 大块内存分配失败

**解决方案**：
1. 创建专用内存管理器 `main/core/memory_manager.cc`：
   ```cpp
   class MemoryManager {
   public:
       // 为 GIF 解码预留 DMA capable 内存池
       static void* AllocateAnimationBuffer(size_t size);

       // 堆监控告警
       static bool IsLowMemory();  // 剩余 < 50KB
       static bool IsCriticalMemory();  // 剩余 < 20KB

       // 内存统计
       static void PrintMemoryStats();
   };
   ```

2. 实现动画资源的延迟加载和卸载：
   - 启动时只加载静态图片
   - 系统稳定后再加载 GIF 动画
   - 内存不足时自动卸载未使用的动画

3. 添加内存保护：
   - 剩余堆 < 50KB 时停止加载新动画
   - 剩余堆 < 20KB 时卸载所有非关键资源

4. 使用 PSRAM（如果硬件支持）：
   - GIF 帧缓冲存储在 PSRAM
   - 减少内部 RAM 压力

**产出文件**：
- `main/core/memory_manager.cc`（新文件）
- `main/core/memory_manager.h`（新文件）

#### 任务 4：日志分级系统

**问题**：
- 日志过多影响性能
- 没有统一的日志管理策略
- 生产环境仍然输出 DEBUG 日志

**解决方案**：
1. 定义统一的日志宏：
   ```cpp
   // main/core/logging.h
   #define LOG_BOOT(tag, format, ...)    // 启动阶段日志（总是输出）
   #define LOG_RUNTIME(tag, format, ...) // 运行时关键日志
   #define LOG_DEBUG(tag, format, ...)   // 调试日志（生产环境禁用）
   #define LOG_PERF(tag, format, ...)    // 性能监控日志
   ```

2. 日志分级策略：
   - **BOOT**：启动流程、硬件初始化（不可禁用）
   - **RUNTIME**：网络连接、音频事件、错误信息
   - **DEBUG**：详细的内部状态（生产版本禁用）
   - **PERF**：性能指标（帧率、延迟、内存使用）

3. 关键路径日志优化：
   - 音频处理路径：仅输出错误和警告
   - 网络通信：仅输出连接状态变化
   - GIF 渲染：移除所有 DEBUG 日志

4. 添加日志开关配置：
   ```cpp
   // sdkconfig
   CONFIG_LOG_LEVEL_BOOT=INFO
   CONFIG_LOG_LEVEL_RUNTIME=INFO
   CONFIG_LOG_LEVEL_DEBUG=NONE
   CONFIG_LOG_LEVEL_PERF=WARN
   ```

**产出文件**：
- `main/core/logging.h`（新文件）
- 全局替换 `ESP_LOGI/ESP_LOGD` 为新宏

##### Step 1：创建通用 HTTP 客户端封装

**文件**：`main/network/http_client.h`
```cpp
class HttpClient {
public:
    struct Response {
        int status_code;
        std::string body;
        bool success;
        std::string error_message;
    };

    // GET 请求
    Response Get(const std::string& url,
                 const std::map<std::string, std::string>& headers = {},
                 int timeout_ms = 5000);

    // POST 请求
    Response Post(const std::string& url,
                  const std::string& body,
                  const std::string& content_type = "application/json",
                  const std::map<std::string, std::string>& headers = {},
                  int timeout_ms = 5000);

private:
    // 内部封装 ESP HTTP Client API
    esp_http_client_handle_t CreateClient(const std::string& url);
    Response ExecuteRequest(esp_http_client_handle_t client);
    void CleanupClient(esp_http_client_handle_t client);
};
```

**实现要点**：
1. 完整封装 ESP HTTP Client 生命周期
2. 统一错误处理（网络错误、超时、HTTP 错误）

## 🏗️ 阶段三：动画系统架构重构

### 3.1 问题根因分析

基于 4 次失败修复的教训：

#### 根本原因
1. **GIF 解码占用过多 CPU**
   - 25 FPS 的解码速度需要大量计算
   - 与音频处理（AEC）抢占 CPU 资源
   - LVGL 定时器 5ms 周期过快

2. **内存管理混乱**
   - 动态分配大块内存导致碎片化
   - 没有预留 GIF 解码专用内存
   - 内存耗尽时没有保护机制

3. **任务调度不合理**
   - LVGL 任务与音频任务优先级冲突
   - GIF 解码阻塞主线程
   - 看门狗超时（单次解码时间过长）

### 3.2 优化方案

#### 方案 1：异步解码 + 帧缓存

**设计思路**：
- GIF 解码在低优先级任务中进行
- 预解码 3-5 帧，存入环形缓冲区
- LVGL 绘制时直接取缓存帧，无阻塞

**实现**：

```cpp
// main/display/lvgl_display/gif/async_gif_renderer.h
class AsyncGifRenderer {
public:
    // 启动解码任务
    bool Start(const std::string& gif_path, int fps = 15);

    // 停止解码
    void Stop();

    // 获取下一帧（非阻塞）
    lv_img_dsc_t* GetNextFrame();

    // 检查是否有缓存帧可用
    bool HasFrameReady();

private:
    // 解码任务（低优先级 FreeRTOS 任务）
    static void DecodeTask(void* param);

    // 环形帧缓冲区
    struct FrameBuffer {
        lv_img_dsc_t* frames[5];  // 最多缓存 5 帧
        int write_index;
        int read_index;
        SemaphoreHandle_t mutex;
    } frame_buffer_;

    TaskHandle_t decode_task_;
    bool running_;
};
```

**优势**：
- ✅ 解码与绘制解耦
- ✅ 不阻塞主线程
- ✅ 音频任务不受影响

#### 方案 3：内存保护

**问题**：
- GIF 解码器动态分配内存，可能导致碎片化
- 没有内存不足时的保护机制

**实现**：

```cpp
// main/core/memory_manager.cc
class AnimationMemoryPool {
public:
    // 初始化时预分配内存池
    bool Initialize(size_t pool_size = 2 * 1024 * 1024) {  // 2MB
        if (heap_caps_get_free_size(MALLOC_CAP_SPIRAM) > pool_size) {
            // 优先使用 PSRAM
            pool_ = heap_caps_malloc(pool_size, MALLOC_CAP_SPIRAM);
        } else {
            // 回退到内部 RAM
            pool_ = heap_caps_malloc(pool_size, MALLOC_CAP_DMA);
        }
        return pool_ != nullptr;
    }

    // 从内存池分配
    void* Allocate(size_t size) {
        if (allocated_ + size > pool_size_) {
            ESP_LOGE(TAG, "Animation memory pool exhausted");
            return nullptr;
        }
        void* ptr = (uint8_t*)pool_ + allocated_;
        allocated_ += size;
        return ptr;
    }

    // 重置内存池（帧切换时调用）
    void Reset() {
        allocated_ = 0;
    }

private:
    void* pool_;
    size_t pool_size_;
    size_t allocated_;
};
```

**保护策略**：
1. 启动时预分配 GIF 解码专用内存池（2MB）
2. 优先使用 PSRAM（如果硬件支持）
3. 限制单个 GIF 最大尺寸：
   - 分辨率：≤ 320x240
   - 帧数：≤ 30 帧
   - 总大小：≤ 2.3MB
4. 运行时检查：
   - 剩余堆 < 100KB 时拒绝加载新动画
   - 剩余堆 < 50KB 时卸载当前动画
